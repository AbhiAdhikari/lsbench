# lsbench results — series 2026-09-20, Claude Sonnet 5

Three life-sciences MCP servers, one model, 25 hand-verified tasks, three
repeats each. Every number below is reproducible from
[`published/2026-09-20-sonnet-5/`](../published/2026-09-20-sonnet-5/): the
per-task results, the full transcripts, and a hash-chained provenance ledger
of every tool call with the upstream data release at the time.

**Status: maintainers have not yet been notified.** Under the fairness rules
this series is not final until the issues in [`issues/`](issues/) are filed and
maintainers have had a chance to respond. Treat the numbers as provisional.

## What the transcripts show

### Routing saturated. The thesis did not survive contact.

Every server routed correctly on every repeat: 39/39 first calls went to an
acceptable tool, with 6 distractor tools loaded and, for the community server,
68 tools of its own. The original thesis — that one-tool-per-endpoint servers
would fail tool selection under distraction — is **not supported** at this model
tier. Two Opus 5 smoke runs (n=1, [`published/2026-09-20-opus-5-smoke/`](../published/2026-09-20-opus-5-smoke/))
saturated the same way.

Two possible readings, both of which the benchmark can test and this series
cannot separate: (a) current models route well enough that description quality
no longer separates servers with ≤ 75 tools; (b) the distractor set is too easy
— a clinical-trials server and a literature server are not confusable with a
target–disease server. Harder distractors (a second Open Targets wrapper, a
UniProt server) are the next experiment.

### The servers separate after the first call, not at it

**otp-community** answered every correctness task, but 48% of the calls made
to it errored. Two of its tools are broken against Open Targets release 26.06:
`search_entities` (35 errors) and `get_target_known_drugs` (20 errors) —
hardcoded for `Target.knownDrugs`, which 26.06 renamed to
`drugAndClinicalCandidates`. What the model sees is
`Error calling tool 'get_target_known_drugs'`; the GraphQL message that would
explain it is written to the server's stderr and discarded. The model recovered
every time by falling back to the server's raw `graphql_query` tool and
introspecting `__type(name: "Target")` — 9 to 12 rounds. On the third repeat of
`ot-recover-002` it hit the 12-round cap before answering, which makes the task
unstable and the strict recovery score 0%. That number is the *cost* of
recovering from an information-free error, not an inability to.

**otp-official** errored on 11% of calls, all model-authored: Sonnet wrote
GraphQL for a field that no longer existed, got the error in-band with the
message intact, and fixed it next turn. Its cost is elsewhere: the
schema-discovery tools return 57–107k characters per call, so both budget
tasks fail the cap and `ot-route-002` took 6–10 rounds. The design trades
bounded responses for a model that composes its own queries and never meets a
stale hardcoded one.

**geomcp** has no lookup-by-accession tool and no way to return sample
characteristics. `search_geo_samples` for GSM5354513 gives a title and a
source tissue; `download_geo_data` fetches the SOFT file (it worked on every
attempt in this series) but no tool reads it back, so the model can see that
the file exists and not what is in it. `geo-correct-004` (clinical subtype of
a sample) scored ½ on all three runs: tissue yes, subtype structurally
unreachable. Its budget results are raw esummary dumps of 17–18k tokens with
no total or truncation marker; `geo-budget-002` is unstable because disclosure
depends on whether the model happened to call `search_geo` (reports
`total_count`) or `search_geo_series` (does not). 16% of calls to it errored,
all of them `"Empty id list - nothing todo"` — the message E-utilities gives
for no hits, passed through as a success, which is why `geo-recover-001`
(a nonexistent accession) was unexercised on two of three runs: there was no
error to recover from, just an empty list. The model said "not found" anyway.

### Silent nulls, on both Open Targets servers

`ot-recover-001` asks about `ENSG99999999999`. Both servers return
`{"target": null}` as a success. The model handled it correctly every time
("no record for that ID"), but there is no error to recover *from*, so the
task is unexercised on both — 6 of the 9 unexercised runs in the table; geomcp's `"Empty id list"` accounts for two more, and one is a harness failure. A
lookup that returns null for a nonexistent ID is a defensible API contract;
it is also exactly the case where a model with weaker instincts invents a gene.

### Correctness is not where these servers differ

24/24 on the Open Targets pair. geomcp's 86% is one task it structurally
cannot answer, three times. Every value the models reported was present in a
tool result, with two "unsupported" flags that are the scorer catching an
answer that *mentions* a value without asserting it ("a subtype field, e.g.
ER+/HER2+, is not exposed") — no credit given, which is the right call, but
not a hallucination.

## Caveats

1. **The geomcp series was run twice.** The first run's machine had 4.7 GB
   free and geo-mcp refuses downloads below 2 × `max_file_size_mb` (10 GB at
   default), so every download errored for environmental reasons. It is kept
   under [`published/superseded/`](../published/superseded/) and replaced by a
   same-day re-run with `--max-file-size-mb 500`. Two harness bugs surfaced in
   the re-run and were fixed before rescoring: the error-detection regex read
   `GSM5354513` as an HTTP 513 (inflating geomcp's error rate to 25%), and a
   4,096-token output cap truncated one answer mid-thought (now 16,000; that
   run is counted as a harness failure, not a server score).
2. **n=3.** Enough to detect instability, not to estimate it. Instability is
   reported as a failure precisely because three runs cannot say more.
3. **No LLM judge; every claim is a string or numeric check.** One scorer
   false positive was found and fixed during this series (GEO returns
   `"gpl": "18573"` for `GPL18573`; the support check now knows). Scores are
   from a rescore under rules `cf2890710914…`; the original `report.json` files
   are kept beside the rescored ones.
4. **Tool names carry the server id**, which is what real clients show a
   model but does leak "clinicaltrials" into the distractor-routing tasks.
5. **Disclosure detection is regex**, over prose and common JSON keys. A
   server that discloses truncation some other way is under-scored; every raw
   result is in `trajectories.jsonl` and `lsbench rescore` re-scores under
   edited rules without API calls.

## Reproduce

```bash
cd lsbench && uv venv && uv pip install -e ".[dev]"
export ANTHROPIC_API_KEY=... GEOMCP_EMAIL=you@example.org
lsbench compare otp-official otp-community geomcp --repeats 3 --model claude-sonnet-5 --max-usd 12
```

Upstream data will have moved since 2026-09-20; `provmcp replay` on any
`provenance.jsonl` in `published/` reports which calls now return different
data and which releases changed.
